Date: 2026-11-18.  Raw output: `2026-11-17-tree-cap-raw.txt` (same
directory).  Gate rows that reach the bound with a small build-time cap
are in `test/proc_gate.sh` ("tree bound"); this run checks the real
default.

## What was run

- cmc: built from `wip/2.1-engine` at "Make the order in which nodes
  run a search choice" when it sat on the race work (0662485 on
  9220e8d; 872b1d9 after the later rebase onto the coverage work): items
  1 and 4 and the node-order change, before item 2, which does not touch
  the search.  `cmc --version` says 2.0.0, since the version is
  not bumped until release.
  gcc 16.2.1, the Makefile's `-O2 -g`.  sha256 of the binary in the raw
  file.  `CMC_TREE_CAP` at its default, 1000000.
- Fixture: `test/proc/threadpos.c` in mode `spin2`: two workers each
  write an unchanged state record forever, and the main thread joins
  the first.  Every world has a multi-threaded node, so none is merged,
  and each has two successors (which worker runs next).  Model:
  `[target] nodes = 1, args = spin2`, invariant `node[0][0] == 0`.
- Command, from the run directory: `./cmc --model-file spin.model`, no
  `--max-states`, no `--depth`, run by `meas.sh`, which records wall
  time and samples the process's peak resident set (VmHWM) every 10 s.
- Host: the libcmc EC2 dev host, Fedora 44, Linux 7.3.4, 32 vCPU, 61 GiB.
  Load average 2.3 at the start and 2.3 at the end; other cmc runs
  (gates, a coverage build) shared the host, each single-threaded.

## Result

```
INCOMPLETE (no violation found): 1000000 worlds with a multi-threaded
node were searched without merging (set the bound with --max-states);
1000000 distinct states, 1131055 left on queue, 0 cut at depth -1,
6691.8 s
```

- Exit status 2, at 1,000,000 worlds, with the bound's message.
- Wall time 6,694 s (1 h 52 min), about 150 worlds a second.
- Peak resident set 203,624 kB (199 MiB) at the last sample: the
  frontier holds 1.13 million action sequences.

## A first attempt that did not finish

The obvious fixture, `threadpos spin` (one endless worker), makes the
tree a chain: every world has one successor, so world n is reached by a
replay of n actions and the search is quadratic.  On the 2.0.0 build
2,000 worlds took 6.8 s, 8,000 took 33 s and 30,000 took 157 s.  A run
of it to the default was stopped after 5 h 31 min (19,865 s) with its
resident set near 1.9 GiB and far from the bound.  `spin2` branches, so
a breadth-first search reaches a million worlds at depth about 20 and
each replay stays short.  The bound is the same branch of the code in
both; only the cost of reaching it differs.

## What this does not show

The run reached the bound once, on one fixture and one host.  It says
nothing about how fast a real threaded program reaches it, which
depends on how long each replay takes.  A bound of 1,000,000 worlds that
a chain-shaped program cannot reach in hours is a limit a user meets as
a long run, not as INCOMPLETE: `--max-states` or `--time` is the way to
bound such a search.
