# Plan: 2.1, closing the process engine's boundaries

Status: open.  Base: `82e8c11` (2.0.0).  Branch: `pr/2.1`.

## Why

2.0.0's cmc(7) and qualification table list four things the process
engine does not see.  Each one can turn a real bug into a pass:

1. `sendmsg` on an fd below 500 is not intercepted, because the launch
   child itself sends the seccomp listener to the checker with
   `sendmsg` after the filter is in.  A worker thread can send on a
   kernel socket the other thread reads, and the scheduler never sees
   it.
2. `lseek`, `openat`, `fsync` and the rest of the file system are not
   intercepted.  A file a node writes survives into the next replay and
   past a crash, which the world does not hold, so a replay can diverge
   or a crash test can pass on bytes the model never accounted for.
   Between threads, a shared offset changes under `lseek` unseen.
3. Interleavings of plain memory accesses between two system calls are
   not explored.  A data race with no system call between the racing
   accesses passes.  The 2.0.0 scheduler explores only the order of
   visible calls, and its tree search makes that exhaustive, but a
   mutex the C library takes without a system call (the uncontended
   fast path) is not a choice point, nor is an atomic.
4. The default bound on the tree search (1,000,000 worlds with a
   multi-threaded node) is never reached by a gate row, so a regression
   in that branch would ship.

Coverage was never measured.  [measured, 82e8c11, Fedora 44, gcc 16
`--coverage`, every gate in `make check`]: functions 96.7% (264/273),
branches 69.6% (3470/4985).  `cmc_cli.c` has 54% of its branches
covered and `cmc_preload.c` 29%.

## 1. sendmsg below fd 500

The listener handoff moves out of the filter's reach instead of the
filter growing an exception.

- The parent seizes the child with ptrace right after `fork()`, adding
  `PTRACE_O_TRACESECCOMP`, and only then lets it run (a byte on the
  socketpair).
- The child installs the first filter as now (`NEW_LISTENER`, every
  intercepted call to `USER_NOTIF`, `sendmsg` only at fd 500 and above),
  sends the listener, then installs a second filter that returns
  `SECCOMP_RET_TRACE` for `sendmsg` below fd 500.  Filters stack, and
  the kernel takes the most severe action of all of them: `USER_NOTIF`
  wins over `TRACE`, which wins over `ALLOW`, so an owned fd is still
  answered by the first filter.
- The engine handles the `PTRACE_EVENT_SECCOMP` stop.  In a node with
  one thread it resumes the call to the kernel (`PTRACE_CONT`).  In a
  node with more than one thread it refuses, exit 3, as
  `kernel_fd_call()` does for every other kernel fd.
- The socketpair is `SOCK_CLOEXEC`, so its end does not leak into the
  node.

Gate: a worker thread that sends on a socketpair the main thread reads
passes on 2.0.0 and is refused now.  A single-threaded node that uses
`sendmsg` on a kernel socket (a Unix socketpair to itself) still runs.

## 2. The file system

A node's view of the file system must be the same on every replay and
must not carry state across a crash that the world does not hold.  The
rule: **the file system is read-only to a node.**  Durable state goes
through fd 193, which the world holds and a crash keeps.

- `open`, `openat`, `openat2` and `creat` are intercepted.  A read-only
  open goes to the kernel.  An open that can change a file (write
  access, `O_CREAT`, `O_TRUNC`, `O_APPEND`, `O_TMPFILE`) ends the check
  with exit 3, naming the path, except `/dev/null`.
- Calls that change the namespace or metadata are refused (exit 3):
  `unlink`, `unlinkat`, `rename`, `renameat`, `renameat2`, `mkdir`,
  `mkdirat`, `rmdir`, `link`, `linkat`, `symlink`, `symlinkat`,
  `truncate`, `mknod`, `mknodat`, and the `chmod`, `chown` and
  `utimensat` families.
- `lseek`, `fsync`, `fdatasync`, `ftruncate`, `fallocate`, `flock` and
  `sync_file_range` are intercepted.  On a checker-owned fd they get
  Linux's answer for a socket (`lseek`: `ESPIPE`; `fsync`, `fdatasync`:
  `EINVAL`) or a refusal where Linux's answer is not modelled.  On fd 193
  `fsync` and `fdatasync` succeed (the record is durable when written).
  On a kernel fd they go to the kernel in a single-threaded node and are
  refused in a multi-threaded one, like every other kernel-fd call.

Gate: a node that writes a file, crashes and reads it back on restart
passes on 2.0.0 (the file survives outside the world) and is refused
now; a worker `lseek` on an fd main also reads passes on 2.0.0 and is
refused now; reading a configuration file still works.

## 3. Memory interleavings

Two layers, so that a pass means something with or without a rebuild.

**Synchronisation as choice points (any binary).**  The preload wraps
the pthread mutex, rwlock, spinlock, condition variable, semaphore,
barrier and once calls, and C11 `mtx_*` and `cnd_*`.  Before each one
it makes a marker call the filter intercepts (`sched_yield` with a
magic first argument and an operation code), so in a node with more
than one thread every lock and unlock is a scheduler choice point, not
only the contended ones that reach `futex`.  `sched_yield` itself
becomes a visible operation.

**Race detection (an instrumented build).**  `libcmc-race.a` implements
the ThreadSanitizer instrumentation interface.  A target compiled with
`-fsanitize=thread` and linked against it instead of libtsan reports
each memory access and atomic to the runtime, which:

- keeps a vector clock per thread and per synchronisation object, with
  happens-before edges from the wrapped pthread calls, thread create and
  join, and atomics by memory order;
- records, per 8-byte word, the last write and the reads since, and
  reports two accesses from different threads, at least one a write,
  not ordered by happens-before, as a data race: the engine prints both
  sites and the schedule, exit 1;
- makes each atomic operation a choice point (the same marker), so
  orders of atomics are explored as well as orders of calls;
- reports an atomic weaker than `seq_cst` the first time it runs; a
  pass that saw one is INCOMPLETE ("weak memory orders are not
  explored"), since the search runs a sequentially consistent machine.

Outside cmc (no `CMC_STATE_FD`), the runtime does nothing, so the same
instrumented binary runs as a normal program.

**The verdict rule.**  A model in which a node ran more than one thread
without the race runtime cannot pass: the result is INCOMPLETE, naming
the instrumented build.  A violation found is still a violation.
Limits that remain, stated in cmc(7): code not compiled with the
instrumentation (other libraries) is not checked for races; a race the
detector flags may be one a synchronisation edge it does not model
would exclude (a false alarm, never a missed race in instrumented
code); weak memory is not explored.

Gate: an unlocked counter incremented by two threads with no system
call between load and store passes on 2.0.0, is INCOMPLETE uninstrumented
and is a reported race instrumented; the locked counter passes
instrumented; a relaxed atomic makes a pass INCOMPLETE; a
`seq_cst` atomic handoff passes.

## 4. The tree bound

`TREE_CAP` becomes overridable at build time (`-DCMC_TREE_CAP=n`).  The
proc gate builds a copy of cmc with a small cap and checks the
default-bound branch: the message, exit 2, and that `--max-states`
still takes precedence.  The docs gate checks that cmc(1)'s default
matches the source.  One measured run of the real default is recorded
in `docs/measurements/`.

## 5. Coverage

`make coverage` builds with `gcc --coverage -O0`, runs every gate of
`make check` plus the coverage-only drivers, and fails unless function
and branch coverage of `src/*.c` are each at least 90%.  Node-side code
(the preload, the race runtime) runs in processes the checker kills,
so it flushes its counters at each choice point when built for
coverage.  A branch that cannot be reached is deleted, not excluded; an
exclusion marker is allowed only on a defensive check of a libc call
that cannot fail in a test, with a comment saying why, and the report
counts them.  CI runs `make coverage`.

## Order

1, 2 and 4 touch the filter and the answer path and go together; 3 is
new code in the preload and a new runtime; 5 follows both.  An
independent review of 1 to 4 precedes the release, as for 2.0.0.
